# Curated list, NOT sourced from an external dataset - hand-built for one
# specific failure mode found via real testing (case 930204645 threshold-
# tuning stress test, 2026-08-19): spaCy's small en_core_web_sm model can
# mistake a common English noun for a surname when it directly follows one
# of these words, because these words are themselves common first names in
# spaCy's training data ("Ruby Chamber" - a fake storage-ledger label, not
# a person - got tagged PERSON purely because "Ruby" primes spaCy to expect
# a name to follow). See src/validation/validators/corroboration_validator.py
# for how this list is used: a candidate whose ONLY evidence is spaCy AND
# whose first token is in this list needs additional corroboration (dictionary,
# title, or high in-document repetition) before being trusted - spaCy alone
# is not enough for these specific words, unlike ordinary bare tokens.
#
# Deliberately NOT used to reject anything outright - a real person actually
# named "Ruby Chamber" would still be caught by dictionary/repetition
# corroboration like any other name. This only removes spaCy's ability to
# corroborate ON ITS OWN when the span starts with one of these words.
#
# Extended 2026-09-16 to a second collision class: a token that is BOTH a
# real (if rare) first name in assets/first_names/first_names.txt AND a
# common English rank/role/noun word elsewhere in the knowledge base -
# found via a real production scan: "Major" is in first_names.txt (a
# genuine, if uncommon, given name) AND in assets/titles/titles.txt (the
# military rank), so a bare, single-token "Major" - e.g. inside an
# Android dumpsys/log dump, nothing to do with a person - got a
# dictionary_single_token detection and cleared DecisionEngine's
# knowledge-corroboration gate on that alone (ACCEPTED 63 times across 6
# files in real casework, zero of them an actual person). See
# corroboration_validator.py's single_token_dictionary_ambiguous handling:
# words in this list now need the SAME additional corroboration
# (repetition, title, or a full first+last dictionary window hit) whether
# the sole evidence is spaCy OR a single-token dictionary hit.
#
# Extended again 2026-09-16, via scripts/audit_collisions.py: eight more
# words sit in BOTH first_names.txt/last_names.txt AND
# assets/honorifics/honorifics.txt - South Asian honorifics/address terms
# (Shri, Sahib, Sardar - "Mr."/"Sir"/respectful-address equivalents,
# overwhelmingly used as a title prefix or standalone address term, rarely
# a person's actual given name on its own) and words that are BOTH a
# historical title AND a very common modern personal name/surname (Raja,
# Rani, Kumari, Pandit, Thakur - e.g. "Vikram Pandit" the real CEO vs.
# "the pandit" the generic noun). None of these are rejected outright by
# this list, same as every entry above: a full first+last dictionary
# window match ("Raja Sharma"), a title, or in-document repetition still
# corroborates a genuine name fully. This only removes a BARE, single,
# low-frequency occurrence's ability to auto-corroborate purely because
# the word happens to also be in the name dictionary - deliberately left
# OUT of this file: locations.txt's overlap with last_names.txt ("Bello")
# is a different failure direction (a real surname risking a false HARD
# REJECT via LocationValidator, not a false ACCEPT) and needs a different
# fix in that validator, not this corroboration-gate mechanism.
